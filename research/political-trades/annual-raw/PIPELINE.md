# Congress Trading — рецепт сборки бандла

Документ описывает, откуда берутся данные, как они превращаются в бандл и что
в этом процессе пока не работает. Код рецепта лежит в [`recipe/`](recipe/) в том
же репозитории и той же ревизии, что и данные, — иначе «пересобрать как было»
невозможно.

около 30 минут.

Каталог Палаты — это только индекс «кто что подал». **Сделок в нём нет**: они
существуют исключительно внутри PDF.

## Инкрементальность

Источник правды — `data/filings/filings.parquet`. По каждому файлингу там
хранится `source_sha256`, `pdf_class`, `extractor`, `extract_status` и
`n_rows`. Пересборка сводится к diff свежего каталога против этой таблицы:
качается и разбирается только новое.

`extract_status`:

| Статус | Значение |
|---|---|
| `pending` | ещё не обрабатывался |
| `ok` | извлечено, строки в бандле |
| `no_transactions` | обработан, сделок нет (пустой PTR — легальный случай) |
| `needs_ocr` | текстовый слой не читается, ждёт GPU-джоб |
| `ocr_failed` | VLM отработал, валидного результата не дал |
| `needs_review` | требует человека |

Отказ 403 статус не меняет: файлинг остаётся в очереди. Портал прикрывает
поток при высокой параллельности — на первом прогоне годовых восемь потоков
дали 6 869 отказов из 15 921 запроса, поэтому по умолчанию их четыре с паузой
0.15 с.

**Индекс только дополняется.** Портал Клерка переписывает исторические
каталоги: между снимком апреля 2026 и августом 2026 из каталога 2012 года
исчезли 4 305 деклараций (все — годовые отчёты и поправки до STOCK Act),
добавилось ноль. Поэтому строка, пропавшая из свежего каталога, не удаляется —
у неё просто перестаёт обновляться `last_seen_at`, и она считается отозванной.
Отметки времени монотонны (`last_seen_at` только растёт, `first_seen_at` только
уменьшается), чтобы вливание старого снимка не помечало живые записи
отозванными.

## Каскад извлечения

Прежний пайплайн отправлял каждый PDF в LLM через OpenRouter — сначала на
классификацию, потом на извлечение. Это было невоспроизводимо (хостовая модель
плюс плагин-конвертер), упиралось в rate limit и стоило двух обращений на
документ. Сейчас:

**1. Классификация — `pdf-inspector`** (MIT, Rust). Возвращает
`text_based` / `mixed` / `scanned` / `image_based`. Детерминированно, локально,
без сети. Полностью заменяет прежний шаг `_meta` (~8 000 обращений к LLM).

**2. Разбор по координатам — `house_ptr_parser.py`.** Работает для
`text_based` и `mixed`.

Почему по координатам, а не по тексту: шрифт бланка Палаты рендерится с
разрядкой, и наивное извлечение схлопывает заголовки — `Filing Status`
превращается в `F      S     `, а `Schedule A: Assets and "Unearned" Income`
в `S        A: A          "U       " I`. Собранный markdown это частично лечит,
но переносит ячейку с тикером в конец строки. Координаты дают исходную
табличную раскладку.

Раскладка бланка (x в пунктах, ось y снизу вверх):

```
x≈25   ID
x≈65   Owner              SP | JT | DC, пусто = сам подающий
x≈104  Asset              переносится на следующие строки
x≈262  Transaction Type
x≈327  Date               дата сделки
x≈381  Notification Date
x≈446  Amount             диапазон, тоже может переноситься
x≈525  Cap. Gains > $200?
```

Границы колонок берутся из строки заголовка, а не зашиты числами: бланк
менялся между 2014 и 2026 годами, а заголовки набраны капителью, из-за чего
приходят как `iD`, `owner`, `transaction Date`. В бланках до 2016 года над
датой сделки нет собственного заголовка — её колонка выводится из самих данных.
Строка транзакции опознаётся по паре дат правее колонки актива; конец таблицы —
по названиям следующих разделов (`Asset Class Details`, `Signature` и т. п.).

**3. VLM — только для сканов.** `needs_ocr` уходит в `run_ocr_backfill.py` на
GPU-флейворе. В ежедневном CPU-прогоне модели не вызываются вообще.

### Замер точности

Сверка с прежним LLM-извлечением на 400 случайных PDF (282 текстовых):

| Поле | Совпадение |
|---|---|
| `transaction_date` | 100.0% |
| `notification_date` | 100.0% |
| `transaction_type` | 99.9% |
| диапазон суммы | 99.7% |
| `ticker` | 60.6% |
| `asset_category` | 58.8% |

Число строк совпало в 96.8% документов. Из расхождений парсер нашёл **больше**
строк в 7 случаях и меньше в 2. Проверенный вручную пример: в
`2022-03-09_20020585.pdf` LLM отдал одну сделку, парсер две — и это две разные
сделки, с разными владельцами (`SP` и сам подающий) и разными счетами
(`Inherited IRA - 2016` и `Charles Schwab IRA`).

Расхождения по `ticker` и `asset_category` — не ошибки парсера. В бланках
многих лет этих полей просто нет: в `2014-09-14_20001643.pdf` во всём документе
ноль кодов `[XX]`, а прежний экстрактор возвращал для его строк `[ST]`.
Инструкция того промпта прямо требовала «Infer from context», и модель
заполняла поле всегда — включая `US_TREASURY`, `MUNI`, `US10Y`, `N/A`. Здесь
поле остаётся пустым, а пропуски тикера закрывает справочник названий.

## Годовые декларации

Годовой отчёт (Financial Disclosure Report) даёт то, чего в PTR нет.

**Schedule A — срез активов.** Без него размер позиции неизвестен, а значит
нельзя отличить выход из позиции от подрезки. Каждая строка: актив, владелец,
диапазон стоимости, тип дохода, диапазон дохода, признак сделок крупнее $1,000
за год.

**Schedule B — сделки за год.** Годовой отчёт перечисляет все операции, включая
те, на которые PTR не подавался вовсе. На выборке из 36 деклараций: 2 683
сделки, из них 740 дублируют уже поданные PTR, а **1 943 раскрыты только
годовым отчётом**.

**Schedule D — обязательства.** Раскладка отличается от разделов A и B:
`Owner(25) Creditor(64) Date Incurred(230) Type(313) Amount(496)`. У шкалы
обязательств своя сетка ступеней — она начинается с $10,001, и ступеней
$1–$1,000 и $1,001–$15,000 в ней нет. Без отдельной шкалы студенческий кредит
на «$10,000 - $15,000» не прижимался ни к одной ступени и терял сумму.

Разделы C и E–J (заработанный доход, должности, соглашения, подарки, поездки,
выплаты) — сведения о человеке, а не о портфеле, и не извлекаются.

### Две версии бланка

Бланк менялся около 2022 года, и заголовки разделов в двух версиях выглядят
по-разному, потому что капитель рвёт слово SCHEDULE на куски:

```
2022+   S A: A  "U" I
2014-21 S cHeDule a: a SSetS anD "u nearneD " i ncome
```

Раздел опознаётся по префиксу до двоеточия, сжатому до букв: он должен быть
равен `s<буква>` или `schedule<буква>`. Двоеточие обязательно — без него под
образец попадала бы строка `S A  B I V D` на последней странице.

Это была причина, по которой первый прогон дал `ok` только с 2022 года, а все
3 909 деклараций 2014–2021 годов ушли в «нет сделок». Отдельная ошибка была в
том, что они так помечались вообще: ноль строк из читаемого PDF — это провал
разбора, а не пустая декларация. Теперь парсер возвращает список найденных
разделов, и шаг различает два случая: разделы не нашлись → `needs_review`,
нашлись и пусты («None disclosed») → `no_transactions`.

### Колонки

Шапка раздела повторяется на каждой его странице:

```
Schedule A 2022+:   Asset(25) Owner(259) Value(298) Income Type(s)(380) Income(463) Tx>$1,000(534)
Schedule A 2014-21: asset(26) owner(269) value(308) income(388)         income tx.>(467)
Schedule B:         Asset(25) Owner(280) Date(319)  Tx. Type(402)       Amount(441) Cap.Gains(523)
```

Три колонки справа от стоимости определяются **только позиционно**, по
названиям — никогда. В бланке 2014 года шапка разбита на две строки: «income»
сверху и «type(s)» под ним, из-за чего сопоставление по имени ставило тип
дохода на место суммы дохода и наоборот.

Из потока текста выбрасываются глифы шрифта Marlett (`gfedc`, `nmlkji`) — это
состояния чекбоксов формы Acrobat, и в ячейки суммы или дохода они попадать не
должны.

Начало записи в разделах A и D отличается от переноса по виду денежной ячейки:
у записи там диапазон с тире («$100,001 - $250,000» или оборванный
«$100,001 -») либо литерал `None`, а перенесённый хвост — голое «$250,000» без
тире. Одна цифра до тире допустима: низшая ступень активов печатается как
«$1 - $1,000», и требование трёх цифр её пропускало. Без этого различения перенос названия актива вместе с хвостом суммы
порождал вторую запись на ту же позицию: у Адерхолта из 145 позиций получалось
151, и в обеих половинах сумма терялась.

Хвост добирается строго в границах своей колонки. Без правой границы к хвосту
стоимости приклеивался хвост дохода из соседней колонки, и оба значения
пропадали.

`value_min_usd` пустой там, где в бланке напечатано `None` — это проданные
активы и закрытые счета, форма перечисляет их без оценки. Проверено на
GSK, Navistar и Bankfirst: извлечение соответствует бланку.

### Дата раскрытия Schedule B

В годовой декларации нет колонки уведомления, поэтому `notification_date` =
дата подачи отчёта. Раньше подачи эти сделки публичными не были, и для
бэктеста это единственная корректная точка входа информации.

Дедуп против PTR идёт по ключу
(bioguide_id, дата сделки, тикер, тип, нижняя граница суммы, владелец).
Приоритет у PTR: он раскрыт на месяцы раньше. Дублирующая строка Schedule B
получает `superseded_by` с `id` строки PTR — не удаляется, чтобы обе формы
раскрытия оставались видимыми.

## Нормализация

Шаг 30 приводит извлечения обеих палат к единой схеме. Что именно чинится:

**Канонизация значений.** 31 вариант `transaction_type` (`P`, `S`,
`S (partial)`, `Purchase`, `Exchanged`, `REDEMPTION`, `Sale (Full)`, …) сводится
к 8; 20 вариантов `asset_category` — к 8. Сравнение регистронезависимое:
капитель бланка отдаёт `s (partial)` вместо `S (partial)`. Прежняя карта
покрывала 3 значения из 31, остальное попадало в бандл как есть.

**Границы сумм** прижимаются к официальным ступеням Ethics in Government Act.
Пара `(1000, 15000)` встречалась в 21 808 строках — модель списывала нижнюю
границу как $1,000 вместо $1,001. Пары, не похожие ни на одну ступень
(`(20, 20)`, `(0, 0)` — количество акций, утёкшее в поле суммы), помечаются
`amount_quality = "invalid"`, а не подгоняются.

**Партия и штат — на дату сделки.** Прежний код брал их из последнего срока
полномочий, поэтому сделке 2015 года у сменившего партию конгрессмена
приписывалась его сегодняшняя партия. Справочник `legislator_terms` разбит по
`party_affiliations`, которые фиксируют переход внутри срока: у Ван Дрю срок
2019–2021 записан как Republican, но до 18.12.2019 он был демократом.

**Владелец** заполняется и для Палаты. Раньше колонка `owner` была пустой во
всех 119 568 строках, хотя код (`SP`/`JT`/`DC`) напечатан в строке актива.

**Мультитикерные ячейки Сената.** Корпоративные действия пишутся как `'T  WBD'`
— две бумаги в одной ячейке, разделённые двойным пробелом. Разносятся в
отдельные строки.

**Поправки Сената.** Поправка переподаёт отчёт целиком, поэтому исходный
скрапер складывал в один файл и оригинал, и поправку — 984 дублирующие строки.
Оригинал помечается `superseded_by` с `id` поправки; строки не удаляются, чтобы
обе версии оставались видимыми.

**Тикер по названию.** Датасет учит сам себя: строится словарь
`нормализованное_название → тикер` по строкам, где тикер напечатан, и
применяется к строкам, где его нет. Название нормализуется снятием тикера в
скобках, юридических хвостов (`Inc`, `Corp`, `Common Stock`, `Class A`) и
пунктуации, так что `Apple Inc. - Common Stock (AAPL)` и
`Apple Inc. Common Stock` дают один ключ. Значение принимается, только если
название встретилось не меньше двух раз и не меньше 90% этих раз указывало на
один тикер. Источник каждого значения — в `ticker_source`.

**Тикер отделён от прочих идентификаторов.** В колонке `ticker` остаётся
только то, что похоже на биржевой тикер (`^[A-Z]{1,5}(\.[A-Z])?$`). Всё
остальное, что бланк назвал в этой графе, переезжает в `asset_identifier`:
CUSIP (`US912810`, `02765UFF6`), купонные заглушки муниципальных облигаций
(`JST-E`, `CD-EX`), иностранные листинги (`1128.HK`, `0QZI.IL`), названия
фондов (`JOVE EQUITY FUND I, LP`). Это 4 291 строка на 1 954 различных
значения. Раньше они лежали в `ticker`, и шаг фич агрегировал по ним как по
бумагам: в `daily-by-ticker.parquet` публиковалось 1 921 «тикер», которого не
существует. Значение не теряется — оно просто лежит в графе, честно
называющей, что это.

**Сделка раньше вступления в должность.** Дата, отстоящая больше чем на два
года до начала первого срока члена, помечается `date_quality =
"before_tenure"`. Это почти всегда неверно прочитанная цифра года; выбрасывать
строку нельзя — документ такой, — но и молча выдавать за нормальную дату тоже.

**Разрешение имён.** Каскад: точное совпадение фамилии и имени (включая
прозвища — `Tommy` Tuberville подаёт декларации под ним) → фамилия и первая
буква имени → фамилия со разведением по штату и дате. При неснимаемой
неоднозначности возвращается пусто: приписать сделку случайному однофамильцу
хуже, чем оставить `bioguide_id` пустым. Не разрешилось 0.27% строк.

## PIT-вид

Второй вид тех же сделок, по контракту из прежнего скелета репозитория
(`recipe.py`, «ziplime PIT recipe, design doc §9»):

```
системные: entity_id, event_date, knowledge_date, knowledge_estimated
значения:  representative, chamber, transaction_type, asset_ticker,
           amount_low, amount_high, disclosure_lag_days, knowledge_source
```

В ziplime 1.20.9, который лежит в репозитории, этого контракта нет — там только
`MARKET_DATA` и `CUSTOM`, и рабочий путь ингеста идёт через `data/trades`. Но
PIT-схема выражает то, чего контракт 1.20.9 не умеет: явную дату, когда факт
стал известен, и признак того, что она оценена, а не прочитана из документа.
Поэтому публикуются оба вида.

`knowledge_date` определяется так: день подачи отчёта, если он есть и
правдоподобен; иначе `notification_date`; иначе статутный предел STOCK Act,
дата сделки плюс 45 дней, и `knowledge_estimated = true`. Неправдоподобная дата
приравнивается к отсутствующей: оценка честнее заведомо ложной даты. Какой из
трёх источников сработал, пишется в `knowledge_source` — оценка и прочитанная
дата суть разные свидетельства, и различать их должен потребитель, а не
догадка. На текущем наборе день подачи покрывает 174 057 строк, уведомление —
416, статутная оценка не срабатывает ни разу.

Раньше ключом было `notification_date`, и это была ошибка. На бланке Палаты это
день, когда податель **узнал** о сделке в управляемом счёте, а не день, когда
отчёт увидел рынок: у 42% строк подача позже, медианный лаг по PTR — 15 дней
против настоящих 28, а у 15.6% строк уведомление совпадало с датой самой
сделки, чего для даты публикации не бывает. Стратегия на таком ключе входила в
позицию за две недели до того, как отчёт стал публичным. После перехода на день
подачи доля нулевого лага — 0.198% (354 строки), отрицательных лагов нет.
Уведомление осталось в схеме `trades`: само по себе оно осмысленно, ключом
быть перестало.

Правило живёт в `knowledge.py` в одном экземпляре, потому что нужно двум шагам:
PIT-виду и дневным фичам. До этого фичи считали свою дату сами и датировались
уведомлением — тот же сдвиг на медианные 13 дней, но в другом файле.

Отбор идёт по дате сделки, а не по общей отметке `date_quality`. Она
становится `unparsed`, если пуста любая из двух дат, и отсев по ней выбрасывал
бы строки с известной датой сделки и неизвестной датой подачи — то есть ровно
те, для которых статутная оценка и нужна.

Таблица пишется **только дополнением**, как требует PIT-инвариант из прежнего
`ingest.py`: новый прогон добавляет строки, которых не было, и никогда не
меняет и не удаляет существующие. Дедуп идёт по хешу строки без `ingested_at`.
Повторный прогон дописывает ноль строк — это проверено.

Инвариант защищает историю раскрытий, но не ошибки извлечения. Если
переизвлечение изменило уже записанные строки — например, парсер перестал
выдумывать потолок открытого диапазона, — тихое дописывание оставило бы в
таблице две противоречащие версии одного факта. Поэтому шаг сравнивает свежий
вид с таблицей и, обнаружив больше 0.5% исчезнувших строк, останавливается и
требует явного `--rebuild`. В расписании такого флага нет: пересборку включает
оператор, запуская job один раз с `CONGRESS_PIT_REBUILD=1`. Смена правила даты
знания — как раз такой случай, и первый прогон после неё делается так.
Один раз страж уже сработал: после правок парсера
10 615 строк из 189 007 перестали соответствовать документам, и таблица была
пересобрана.

`manifest.json` держит относительный `table_uri`: абсолютный путь, как в
реестре бандлов ziplime, привязал бы бандл к машине, на которой он собран.
`recipe_hash` — sha256 по содержимому каталога `recipe/`, чтобы к каждой сборке
прилагался отпечаток кода, которым она сделана.

## Аудит извлечения

`recipe/audit_extraction.py` сверяет бандл с первоисточником: каждое значение
должно буквально присутствовать в PDF, из которого извлечено. Канонизация
учитывается — прижатую к ступени сумму ищем и в исходном, и в приведённом виде.
Текст документа собирается в порядке чтения (по строкам), иначе между частями
одной ячейки оказываются значения соседних колонок.

    python recipe/audit_extraction.py --sample 200

Результат на 200 документах после исправлений:

| Проверка | Результат |
|---|---|
| PTR: дата сделки, дата раскрытия | 2 351/2 351 |
| PTR: границы сумм, тикеры | все ненулевые сходятся |
| Активы: границы стоимости | 6 785/6 785 |
| Активы: границы дохода | все сходятся |
| Активы: название в документе | 6 889/6 897 (99.88%) |

Инварианты по всему бандлу: ноль сумм вне официальных ступеней, ноль дублей
`id`, ноль перевёрнутых диапазонов, ноль тикеров не в верхнем регистре.

### Что аудит нашёл

Шесть систематических дефектов, все исправлены:

1. **Выдуманные потолки.** Бланк печатает «Spouse/DC Over $1,000,000» —
   открытую ступень без верхней границы. Канонизация подтягивала её к закрытой
   ступени и ставила $5 000 000, которых в документе нет: 620 строк. Прежний
   LLM-экстрактор писал для той же ступени `999999999` и `100000000`, поэтому
   любой потолок выше официального для своей ступени теперь считается не из
   документа, и диапазон остаётся открытым.
2. **Потерянная граница записи.** Ячейка «Spouse/DC Over» с суммой на
   следующей строке не опознавалась как начало записи, и два соседних актива
   слипались в один. Вернуло 727 активов и 67 обязательств.
3. **`Undetermined` в колонке стоимости** — законное значение для минеральных
   прав и пенсионных долей — тоже не считалось началом записи. Вернуло ещё
   2 275 активов. Полный перечень нечисловых значений этой колонки: `None`,
   `Undetermined`, `Spouse/DC Over`, `Over $50,000,000`.
4. **Подпись `LOCATION:`/`L:`** затекала в название актива: «3221 Wheatridge
   LOCATION: Pearland, TX, US». Вынесена в колонку `location`, заполнена у
   25 тысяч активов.
5. **Подпись не в начале строки.** Бланк печатает «IRA DESCRIPTION: Exxon
   Mobil Corporation», и требование метки в позиции 0 отправляло всю строку в
   название вместе со словом DESCRIPTION. Теперь текст до метки отделяется и
   уходит в название.
6. **Сноски и ссылка на справочник** («* Asset class details available…»,
   `https://fd.house.gov/reference/…`) печатаются в колонке актива и попадали
   в его название.

### Сверка парсера с прежним LLM

На 5 699 документах, где есть оба извлечения: детерминированный парсер даёт
53 895 строк против 53 415 у LLM. Точное совпадение по числу строк в 97%
документов, парсер нашёл больше в 158, меньше в 13 (максимум 6 строк на
документ). Паритет или лучше.

Разница в общем счёте объясняется охватом: LLM обрабатывал и сканы через
растеризацию, детерминированный парсер отдаёт их в очередь OCR. Сейчас 73%
строк бандла даёт детерминированный разбор.

## Расписание и ручной запуск

```bash
export CONGRESS_HF_NAMESPACE=<org-или-пользователь>
python scripts/register_jobs.py create
```

Создаётся два расписания:

| Задание | Когда | Флейвор | Стоимость |
|---|---|---|---|
| `congress-refresh` | ежедневно 08:00 UTC | `cpu-upgrade` | ~$0.01/прогон |
| `congress-ocr` | воскресенье 03:00 UTC | `l40sx1` | по факту очереди |

GPU-джоб завершается за секунды, если очередь `needs_ocr` пуста, поэтому
дорогой флейвор оплачивается только когда есть работа. `l40sx1` (48 ГБ) взят
потому, что веса LIFT в BF16 (~20 ГБ) не помещаются комфортно в 24 ГБ
`a10g-small` или `l4x1`.

Ручной запуск вне расписания:

```bash
python scripts/register_jobs.py trigger congress-refresh   # запустить сейчас
python scripts/register_jobs.py list                       # что зарегистрировано
python scripts/register_jobs.py suspend congress-ocr       # приостановить
```

Либо разово, без расписания:

```bash
hf jobs uv run --flavor cpu-upgrade --timeout 2h \
  --secrets HF_TOKEN=$HF_TOKEN -e CONGRESS_HF_NAMESPACE=<ns> \
  https://huggingface.co/datasets/<ns>/congress-trading/resolve/main/recipe/run_refresh.py
```

## Локальный прогон

```bash
cd recipe
python run_refresh.py --no-publish              # все шаги, без публикации
python run_refresh.py --only 00 30 40 --no-publish
python step_02_house_extract.py --limit 50      # отдельный шаг
```

Настройки — через окружение, чтобы оркестратор не пробрасывал пути аргументами:

| Переменная | Значение |
|---|---|
| `CONGRESS_HF_NAMESPACE` | org или пользователь на HuggingFace |
| `CONGRESS_HF_REPO` | полный `namespace/repo`, если имя не стандартное |
| `CONGRESS_WORK_DIR` | рабочий каталог (на HF Jobs — `/tmp/congress`) |
| `CONGRESS_SOURCES_DIR` | куда складывать сырые PDF и GIF |
| `CONGRESS_HOUSE_EXTRACTIONS` | каталоги извлечений Палаты через `:`, последний приоритетнее |
| `CONGRESS_SENATE_JSONL` | путь к извлечениям Сената |
| `HF_TOKEN` | токен для публикации |

Перечисление нескольких каталогов извлечений — это способ миграции: свежий
детерминированный результат перекрывает legacy по тому же `doc_id` по мере
переобработки, без отдельного шага миграции.

## Что не сделано

**Бумажные PTR Сената — 491 файлинг, 29%.** Исходный скрапер сохранял под
именем `{uuid}.pdf` HTML-страницу вьюера: все 491 файла начинаются с
`<!DOCTYPE HTML>`. Настоящие сканы — 1 225 GIF на втором хосте
`efd-media-public.senate.gov`, ссылки лежат в `<img class="filingImage">`.
Из-за этого отсутствуют почти весь 2012–2013 год (тогда бумажными были 100%
файлингов) и 34 сенатора, подававших только на бумаге.

**Сканы Палаты — 2 447 документов.** Доля падает с 60% в 2014 до 12% в 2026.
Очередь `needs_ocr` есть, GPU-джоб под неё написан, прогон не сделан.

**Тикер отсутствует** у 4 094 строк Палаты и 1 690 строк Сената. Часть
принципиально невосстановима (муниципальные облигации, непубличные доли), часть
закрывается расширением справочника названий.

**Лицензионные ограничения** описаны в [README](README.md#licence-and-terms).
Отдельно: веса LIFT под модифицированной OpenRAIL-M — бесплатно для research,
личного использования и компаний с выручкой ниже $5M, нельзя конкурировать с
API Datalab. Переключение на пермиссивную альтернативу (olmOCR-2, Apache-2.0)
предусмотрено переменной окружения в `run_ocr_backfill.py`.
